# Next.js Powerful Redis Caching Note

## 1. What is Caching with Redis?

Caching saves expensive database results or API responses in a fast, in-memory data store.

Redis helps your app:
* Load pages under **10ms**
* Reduce primary database load
* Share cache state across instances
* Set custom expiration timers (TTL)

---

## 2. Caching Flow with Redis

```txt
                       User Request
                            │
                            ▼
                  ┌───────────────────┐
                  │    Check Redis    │
                  └───────────────────┘
                            │
              ┌─────────────┴─────────────┐
              ▼ Cache Hit                 ▼ Cache Miss
     ┌─────────────────┐         ┌─────────────────┐
     │  Return Redis   │         │  Query Postgres │
     │  Stored JSON    │         │   Database      │
     └─────────────────┘         └─────────────────┘
                                          │
                                          ▼
                                 ┌─────────────────┐
                                 │ Save to Redis   │
                                 │  (Set Timeout)  │
                                 └─────────────────┘
                                          │
                                          ▼
                                     Return Data
```

## 4. The Short & Simple Cache Wrapper

Use this streamlined structural pattern to quickly read and update your Redis server strings.

### app/actions/cacheActions.js

```javascript
import { redis } from "@/lib/redis";
import { prisma } from "@/lib/prisma"; // Primary Database

export async function getCachedUserData(userId) {
  const cacheKey = `user:${userId}`;

  try {
    // 1. Attempt reading from memory cache (Hit)
    const cachedData = await redis.get(cacheKey);
    if (cachedData) {
      return { source: "redis", data: JSON.parse(cachedData) };
    }

    // 2. Fetch from source of truth on failure (Miss)
    const user = await prisma.user.findUnique({ where: { id: userId } });
    if (!user) return { success: false, message: "Not found" };

    // 3. Save serialized dataset with a 10-minute expiration window (600s)
    await redis.set(cacheKey, JSON.stringify(user), "EX", 600);

    return { source: "database", data: user };

  } catch (error) {
    // Graceful fallback to raw database if Redis disconnects
    const backupUser = await prisma.user.findUnique({ where: { id: userId } });
    return { source: "database_fallback", data: backupUser };
  }
}
```

## 5. Cache Invalidation (Purging)

When data changes, you **must delete the old key** so users do not see outdated information.

### app/actions/userActions.js

```javascript
import { redis } from "@/lib/redis";
import { prisma } from "@/lib/prisma";

export async function updateUserProfile(userId, newData) {
  // 1. Apply primary updates directly to the database
  const updatedUser = await prisma.user.update({
    where: { id: userId },
    data: newData
  });

  // 2. Clear out stale key references instantly
  await redis.del(`user:${userId}`);

  return { success: true, updatedUser };
}
```

## 6. Execution Command Quick Reference


| Action | Command Syntax | Use Case Example |
| :--- | :--- | :--- |
| **Read Cache** | `redis.get(key)` | Loading structured dashboard user objects |
| **Write Cache** | `redis.set(key, val, 'EX', sec)` | Storing complex database result charts for 1 hour |
| **Delete Cache** | `redis.del(key)` | Dropping stale menu trees upon fresh post creation |
| **Flush All** | `redis.flushall()` | Clearing the entire database during a core production update |

## 7. Critical Execution Rules

### Always Stringify and Parse Objects

Redis saves data natively as basic strings. You cannot pass a raw JavaScript object or array directly into `.set()` without breaking your string storage lines.

```javascript
// ❌ WRONG
await redis.set("profile", userObj);

//  RIGHT
await redis.set("profile", JSON.stringify(userObj));
```

### Implement Safe Try-Catch Fallbacks

If your Redis container goes offline, your entire application should not crash. Always handle Redis operational executions inside a robust block that defaults back to querying your primary database smoothly.
