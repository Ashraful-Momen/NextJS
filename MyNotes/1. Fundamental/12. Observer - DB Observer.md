# Next.js Database Observers Note (Prisma Middleware & Extensions)

## 1. What is a Database Observer?

An observer listens for specific database actions (like creating, updating, or deleting a record) and automatically executes code:
* **Pre-Events (Before)**: Modify data, validate fields, or hash passwords *before* saving to the database.
* **Post-Events (After)**: Send welcome emails, clear Redis cache, or log activity *after* a database change succeeds.

---

## 2. Observer Lifecycle Flow

```txt
       Prisma Action Triggered (e.g., user.create)
                            │
                            ▼
               ┌─────────────────────────┐
               │     PRE-DB EVENT        │
               │  (Hash password, etc.)  │
               └─────────────────────────┘
                            │
                            ▼
               ┌─────────────────────────┐
               │    Database Execution   │
               └─────────────────────────┘
                            │
                            ▼
               ┌─────────────────────────┐
               │      POST-DB EVENT      │
               │  (Clear Redis, Emails)  │
               └─────────────────────────┘
                            │
                            ▼
                   Return Result to App
```

---

## 3. Creating the Observer Instance

In Next.js using plain JavaScript, we achieve the "Observer Pattern" by extending the Prisma client using `$extends`.

### lib/prisma.js

```javascript
import { PrismaClient } from "@prisma/client";

const globalPrisma = new PrismaClient();

// 1. Create the Observer Extension
const prismaWithObservers = globalPrisma.\$extends({
  query: {
    user: {
      // PRE-EVENT: Runs before the database execution
      async create({ args, query }) {
        // Example: Automatically transform email to lowercase
        if (args.data.email) {
          args.data.email = args.data.email.toLowerCase();
        }
        
        // Execute the actual database query
        const user = await query(args);

        // POST-EVENT: Runs after the database transaction succeeds
        await triggerPostUserCreate(user);

        return user;
      },

      // PRE & POST EVENT FOR UPDATES
      async update({ args, query }) {
        // Pre-Event logic here...
        
        const user = await query(args);

        // Post-Event: Clear related cache hooks
        console.log(`[Observer] User ${user.id} updated. Invalidating cache...`);
        
        return user;
      }
    }
  }
});

// Helper function representing a Post-Event trigger
async function triggerPostUserCreate(user) {
  console.log(`[Observer] User created with ID: ${user.id}. Sending welcome email...`);
  // Add your email utility or Redis invalidation logic here
}

// Export the observer-wrapped instance instead of the raw client
export const prisma = prismaWithObservers;
```

## 4. Triggering the Observer

You do not need to call the observer manually inside your Server Actions or API files. It listens silently in the background whenever you invoke your standard `prisma` client.

### app/actions/userActions.js

```javascript
import { prisma } from "@/lib/prisma";

export async function registerUser(data) {
  try {
    // The observer automatically catches this event
    const newUser = await prisma.user.create({
      data: {
        name: data.name,
        email: data.EMAIL_UPPERCASE, // Will be lowercase by Pre-Event
        status: "pending"
      }
    });

    return { success: true, user: newUser };
  } catch (error) {
    return { success: false, error: error.message };
  }
}
```

## 5. Event Mapping Comparison (Laravel vs Next.js)



| Laravel Observer Method | Next.js Lifecycle Hook Equivalent | Execution Type |
| :--- | :--- | :--- |
| `creating()` / `updating()` | `async create()` / `update()` before `await query(args)` | **Pre-Event** |
| `created()` / `updated()` | `async create()` / `update()` after `await query(args)` | **Post-Event** |
| `deleting()` | `async delete()` before `await query(args)` | **Pre-Event** |
| `deleted()` | `async delete()` after `await query(args)` | **Post-Event** |

## 6. Critical Execution Rules

### Always Return the Query Result

Inside your custom observer block, you must return the output of `await query(args)`. If you forget to return this value, your Server Actions will receive an `undefined` response instead of the database object.

```javascript
// ❌ WRONG
async create({ args, query }) {
  await query(args);
  // Missing return statement kills data chain
}

//  RIGHT
async create({ args, query }) {
  const result = await query(args);
  return result; 
}
```

### Keep Post-Events Non-Blocking When Possible

If your post-event includes an action that takes a long time (like a slow external email API), do not use `await` if the user doesn't need to wait for it. Let it execute asynchronously in the background so your user gets an instant response.
